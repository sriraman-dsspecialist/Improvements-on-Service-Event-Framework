# Service Event Framework Improvement

## Objective
This project improves the original Service Event Framework by detecting data quality issues across task list, material, and service event records. It helps identify duplication, conflicting material groups, parent/child disparity, event clustering, and misspelt service event names.

The solution combines:
- SQL-based data extraction from the source database
- Python data processing and validation
- Excel output generation for processed datasets
- A Streamlit dashboard for interactive analysis and review

## Purpose
The main purpose is to give business users and data stewards a reliable way to:
- detect duplicate or inconsistent task lists
- find repeated or conflicting material-group relationships
- highlight parent-child material disconnects
- cluster similar service events and detect spelling issues
- review historical service-event distribution trends

This reduces manual effort and increases confidence in downstream planning and reporting.

## Product overview
The project is structured as a data quality and analytics pipeline. It reads source data from SQL Server or local Excel files, processes it in Python, and saves the output to the configured processed/output folders. A Streamlit interface then exposes the analysis in a user-friendly dashboard.

## High-level workflow
1. Read configuration from `config.yaml`.
2. Fetch source inputs from SQL Server or local Excel files.
3. Process the data for validation and anomaly detection.
4. Save output as Excel files in the processed/output folders.
5. Launch the Streamlit dashboard for inspection and review.

## Key component summary

### `app/`
Contains the Streamlit pages and UI for each analysis module, such as:
- task list duplicity
- material duplicity
- material group conflict checks
- material group mixie analysis
- parent-child disparity checks
- service event clustering and spell check
- event distribution analysis

### `processing/`
Contains the core computation layer. These modules perform actual validation logic, grouping, conflict detection, and output generation.

### `pipeline/`
Contains the data-fetch and extraction layer, including SQL query resolution and retrieval from the database.

### `utils/`
Contains shared configuration, database, logging, and file helpers.

### `queries/`
Stores SQL query files used to fetch source data from the database.

### `data/`
Stores raw, processed, and output files generated by the application.

## Configuration
The project settings are controlled by `config.yaml`. The file defines:
- whether to fetch data
- whether to process it
- whether to launch the dashboard
- source folder locations
- input file names and processed file names

See the dedicated user guide for full configuration details.

## Runtime requirements
The application expects:
- Python 3.10.x
- SQL Server connectivity through `pyodbc`
- a configured ODBC SQL Server driver
- access to the source SQL database used by the project

## Execution
From the project root, run:

```bash
python main.py
```

This will fetch data (when enabled), process it, and launch the dashboard in a browser if `build_app` is set to true in `config.yaml`.

## Dependencies
Dependencies are declared in `requirements.txt` and include:
- pandas, numpy
- SQLAlchemy, pyodbc
- PyYAML, openpyxl
- scipy, scikit-learn
- streamlit, plotly
- sentence-transformers, rapidfuzz, pyenchant
- pytest

## Notes
- The project currently expects a Windows SQL Server environment with the correct database driver available.
- The `pyenchant` dependency is only compatible with the supported Python 3.10 setup described in the user guide.
- The generated `logs/` directory stores runtime information for troubleshooting.
